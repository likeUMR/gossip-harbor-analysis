# 订单提交

一次交付包含输入确认、模型结算与表现三个时间段。普通订单可能先询问仓库；进入模型后先分流特殊/分支，普通路径先发奖再扣物，再处理扣物后的活动与延迟奖励，之后更新历史、补新订单，最后同步与播放表现。

## 本次操作的真实顺序

| 顺序 | 做什么、为什么 | 分支与结束位置 |
| --- | --- | --- |
| 1 | 点击交付：检查按钮、需求与确认分流 | 先检查按钮是否禁用。普通订单读取棋盘中的可用代码数量，逐项核对需求；全部够用才直接提交，缺少时先询问是否使用仓库。特殊订单按钮另走展示窗口，玩家再次点击后才提交。这里的确认尚未发奖、扣物或补位。 |
| 2 | 进入模型：先分流特殊与分支订单 | 进入FinishOrder后先按订单内部类型分流。特殊任务清理相关整条链并发配置奖励；分支任务清理链并把有限奖励池全部发完。这两条路径立即返回，普通订单才继续后面的价格、奖励、逐件扣除和补位顺序。 |
| 3 | 普通交付：算奖励并先发即时奖励 | 普通链先按需求算价格与难度，再按活动资格收集奖励，分出延迟奖励并保存快照。随后发即时奖励、亲密度礼物与Buff奖励，处理订单微笑分数。此时材料尚未扣除，不能把发奖与扣物理解成一个不可分割的事务。 |
| 4 | 标记完成，再逐项扣需求物品 | 先缓存奖励并标完成，再按原需求顺序一件一件扣物。每项先找棋盘，再找仓库；每次都重新统计并刷新订单。两处没有就记错误并继续，源码没有撤销已经发放的奖励。 |
| 5 | 扣物之后：烹饪奖励、宝箱通知与延迟发奖 | 扣除完成后才尝试烹饪狂热奖励，因此刚腾出的格可能成为奖励落点。之后通知宝箱顾客完成，再发之前分离出的延迟奖励，最后才进入所属订单模型的完成与补位。 |
| 6 | 所属模型完成：更新历史，再补订单 | 普通交付寻找仍包含该订单的模型。主订单先更新亲密度、下一次Lucky资格、累计难度与重复链权重；槽位模型再写完成、日志，移除旧槽并按优先级补新订单。补位是多轮且含固定、教程、活动和随机分支，最后才派全局订单完成通知。 |
| 7 | 模型收尾，再播放交付表现 | 所属模型补位与全局完成通知返回后，主棋盘再刷新状态、按资格发首轮微笑提示，检查同步并派局部完成消息。视图收到消息播放棋子飞入、奖励表现和顾客离开；表现不能再次发放已经落账的奖励。 |
