# 所属校验与下一单使用的状态

寻找包含该对象的模型之后，更新影响下一单的状态。Lucky订单保持下一次触发资格，普通订单仅在配置提供机会时抽一次；该Lucky与母体产出Lucky是两个系统。

## 内部处理顺序与目的

1. 找包含旧订单的模型；未找到也不会撤回前面的发奖。

2. 更新Lucky触发资格、累计难度和重复链历史，作为下一单输入。

3. 再交槽位模型完成并补位，注意它的成员校验发生在这些副作用之后。

---

## 演示案例

本例设定本机制所需条件，演示它实际触发后的结果。

### 场景1：普通单取得下一次Lucky资格

**本例情境：** 普通订单属于本模型，本例配置给下一单Lucky触发机会。

**判断与目的：** 完成历史先更新难度，再独立判定下一次Lucky订单资格。

**玩家看到的结果：** 累计难度变109，本次拿到下一次Lucky订单尝试资格；不等于下一单必定创建成功，还要满足槽位和冷却。
