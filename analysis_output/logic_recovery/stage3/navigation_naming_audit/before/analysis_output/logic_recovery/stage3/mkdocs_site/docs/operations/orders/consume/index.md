# 标记完成，再逐项扣需求物品

先缓存奖励并标完成，再按原需求顺序一件一件扣物。每项先找棋盘，再找仓库；每次都重新统计并刷新订单。两处没有就记错误并继续，源码没有撤销已经发放的奖励。

## 本阶段的判断与处理顺序

1. **缓存奖励与完成状态**：完成状态写在扣除之前。完成后的奖励读取走缓存，但缓存首次填充可能重新调用奖励计算，不能认为即时快照就是唯一一次计算。

2. **按棋盘遍历序扣第一件匹配物**：逐项找裸代码相同的第一件棋盘物，不按最近距离或等级挑选。同code重复需求会在后一次扫描找到另一实例。

3. **棋盘未找到才扣仓库**：同一需求只要棋盘已扣到，就不再扣仓库。棋盘找不到时扫描仓库索引，删除第一件匹配物并删除保存属性；缓存不在兜底范围。

4. **逐件刷新与部分失败边界**：每件尝试之后刷新真实数量和其它订单状态。某项没找到也继续处理后面的需求；先发奖再扣物的顺序必须保留，不能用“交付成功”概括所有异常。

---

## 演示案例

下面分别改变前提，让各条分支实际发生；互斥结果属于不同场景。

### 场景1：完成后固定奖励读取

**本例情境：** 8金币已发，订单尚未开始扣物，准备写完成状态。

**判断与目的：** 缓存奖励并标完成，让后面的数量刷新不再把旧单改回可交付。

**玩家看到的结果：** 订单显示完成，之后读到的仍是本次8金币奖励；此步不再发8金币，余额保持108。

### 场景2：按格序消耗两件食物

**本例情境：** 订单已完成，按两件203和一件204的顺序开始扣物。

**判断与目的：** 每项需求都从棋盘第一格重新找，删掉首件精确匹配物。

**玩家看到的结果：** 棋盘两件203都消失，两个格空出；重复需求不会误用同一件棋子，Gold仍108。

### 场景3：缺物才动仓库

**本例情境：** 两件203已从棋盘扣到，最后一件204只在仓库。

**判断与目的：** 只为尚未扣到的需求扫描仓库，删除首个匹配项。

**玩家看到的结果：** 仓库的204被消耗，前两项不会再额外扣仓库203；三件需求合计只扣三件。

### 场景4：确认后第三件丢失

**本例情境：** 玩家确认后仓库204消失，但结算仍已发8金币。

**判断与目的：** 每项刷新一次，缺物记录错误但继续，不撤回已发奖励。

**玩家看到的结果：** 两件203消耗、订单仍完成、金币仍108；204缺失被记录，没有自动补物或退回奖励。
