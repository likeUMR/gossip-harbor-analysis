# 点击交付：检查按钮、需求与确认分流

先检查按钮是否禁用。普通订单读取棋盘中的可用代码数量，逐项核对需求；全部够用才直接提交，缺少时先询问是否使用仓库。特殊订单按钮另走展示窗口，玩家再次点击后才提交。这里的确认尚未发奖、扣物或补位。

## 本阶段的判断与处理顺序

1. **按钮门控与入口差异**：按钮禁用便结束；普通订单进入数量检查，特殊订单先展示需求。音效在门控之后播放，不能把音效当作交付成功。

2. **首次计数只看棋盘**：首次判断不含仓库和缓存。它回答“能否直接从棋盘交付”，不是判断所有持有物是否足够。包装物要按实际代码计数，不能把内含类型当裸物品。

3. **重复需求按件数检查**：逐项核对，同一种物品出现两次就需要两件。失败返回每种代码的缺口，窗口据此展示需要动用哪些仓库物。空需求会通过本方法，不能只依靠方法名假设它必定拒绝。

4. **仓库确认与关闭后的提交**：窗口重新算棋盘缺口并展示，确认只设置提交标记；真正提交在窗口关闭完成后。普通入口只检查订单还在不在槽位，没有再次核对库存，也不会先把仓库物移到棋盘。

5. **特殊订单展示后的再次点击**：特殊窗口先把最多三个需求图像聚到中央，动画初始化之后点击遮罩才提交。它先选独立棋盘对象，没有对象时用仓库图像表现；这一选择不是普通需求扣除算法。

## 演示案例

下面分别改变前提，让各条分支实际发生；互斥结果属于不同场景。

### 场景1：按钮允许提交

**本例情境：** 普通订单按钮已开启，棋盘缺的一件204可以从仓库补交。

**判断与目的：** 允许点击后播放服务音效，再检查棋盘需求。

**玩家看到的结果：** 听到服务音效，出现使用仓库204补交的确认窗；金币仍100，物品未扣。

### 场景2：区别棋盘与总持有

**本例情境：** 棋盘有两件203，仓库和缓存都有204，订单需要两件203和一件204。

**判断与目的：** 首次检查只统计棋盘上的精确代码，仓库和缓存都不参与。

**玩家看到的结果：** 虽然仓库和缓存都有204，仍会出现仓库补交提示；缓存不能替代此次材料扣除。

### 场景3：重复需求缺口

**本例情境：** 棋盘只有一件203，订单却需要两件203和一件204。

**判断与目的：** 每个重复需求都累加需要数量，逐项查出全部缺口。

**玩家看到的结果：** 窗口要求从仓库补一件203和一件204，不能用一件203满足两个需求；此时未扣物。

### 场景4：确认仓库补交

**本例情境：** 玩家确认使用仓库的204补交，关闭期间订单和材料均未变化。

**判断与目的：** 记录确认意愿，关闭动画结束后核订单仍在，再提交。

**玩家看到的结果：** 确认后获得8金币，三件需求都被消耗，订单完成；能量仍10。

### 场景5：特殊订单二次点击

**本例情境：** 任务1的需求物展示已准备完成，玩家再次点击窗口。

**判断与目的：** 先展示需求，再由玩家再次点击确认提交，不沿用普通订单仓库窗。

**玩家看到的结果：** 首次点击只看到任务物聚拢；第二次点击完成任务1，按任务表领15宝石和100能量，余额变35宝石、110能量。
