# 棋子吞噬

只有普通合成失败才读取目标吞噬组件。目标需要这种物品且数量未满时，接收一件，保存进度并删除拖入物；所有需求都完成时变换成奖励物。吞噬成功立即结束，不再交换。

吞噬所需物品通常在目标创建时已经确定，拖入时只比对代码和剩余数量，不在每次拖动时重新随机需求。

## 判断与分支（按触发位置）

1. **吞噬需求与资格**：目标创建时为最多两项需求选代码和数量。玩家拖入时按完整物品代码检查需求是否尚缺；目标是否允许点击影响移动资格，但不是拖入吞噬的额外门槛。
2. **吞噬进度**：匹配后先更新目标进度并保存，再删除拖入物、通知吞噬与刷新进度。最后检查全部需求是否完成；未完成则保留目标等待下一件。
3. **吞噬完成变换**：全部需求完成后，目标按变换权重选一个结果并原格替换。吞噬引起的变换不再额外消耗点击能量；不允许点击的吞噬物还会震动邻格，随后发全局吞噬完成通知。

## 演示案例

下面分别改变前提，让各条分支实际发生；互斥结果属于不同场景。

### 场景1：有限池确定吞噬需求

**本例情境：** 创建一个需要吞入食物的目标，并把201拖向它。

**判断与目的：** 创建目标时打乱有限份额并消费一份；拖入时只比需求，不重新抽奖。

**玩家看到的结果：** 这个目标需要吞入两件201；拖入201会被接受。下一目标继续使用剩余份额，本次拖入没有重抽需求。

### 场景2：吞入第一件但尚未完成

**本例情境：** 目标需要两件201，尚未吞入任何一件，玩家拖入第一件。

**判断与目的：** 接受尚缺的一件，保存进度并删拖入物，再检查是否完成。

**玩家看到的结果：** 201消失，目标从0/2变1/2，还需一件201；本次没有奖励变换，也不交换。

### 场景3：最后一件触发奖励变换

**本例情境：** 目标需要两件201，已吞一件；玩家拖入最后一件，变换奖励配置有效。

**判断与目的：** 补齐需求后独立按权重选奖励，目标原位变换。

**玩家看到的结果：** 拖入201和吞噬目标都消失，目标格出现203，能量仍10；这次不走普通气泡或金币奖励。
