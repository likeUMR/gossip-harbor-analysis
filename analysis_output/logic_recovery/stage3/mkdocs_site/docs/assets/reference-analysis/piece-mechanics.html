商店刷新：费用、次数与递增

钻石手动刷新：20 钻/次。解包的 ShopDataModel.GetRefreshGemCost() 直接返回常量 20；ShopModel.RefreshFlashSaleByGemCost() 每次点击都用这个值调用钻石扣除。

一天能刷多少次：客户端没有固定每日上限。这条付费路径没有读取或递增“今日已刷新次数”的计数器，按钮逻辑只检查当前钻石是否足够。因此从客户端代码能确认的是：在有足够钻石、商店功能已开放时，可继续按 20 钻/次刷新；不能从解包代码推出“每天 N 次”的硬上限。

费用不递增。刷新次数不会作为参数参与费用计算，首次和后续手动刷新都取同一个 20。广告刷新是独立路径，调用 AdModel.ShowAd(EAdType.ShopRefresh)，其广告次数/配额不等于钻石刷新次数，当前解包也没有可确认的每日广告次数数值。

不要混淆自动刷新：每日特惠（DailyDeals）按服务器日界线自动换一轮；普通闪购的自然刷新时间由服务端配置读取。它们是定时刷新，不是“每天可付费刷新次数”。

两层库存与 CD 状态机

每个母体实例只有一组 itemRestNumber（批次储备）和 storageRestNumber（总库存）。同一母体产出的所有 series、等级共享这两层计数器。

1 · 点击产出

按 Weight_i / ΣWeight 抽取；普通点击库存固定扣 1。
→

2 · 批次 CD

itemRestNumber = 0 时启动 ItemRecoveryDuration；结束后批次补回 ItemMaxNumber，并扣总库存。
→

3 · 总库存 CD

总库存也归零时启动 StorageRecoveryDuration；结束后两层都补满。

普通点击：P(产出 i) = Weight_i / ΣWeight；每次实际扣减 = 1；E[单击扣减] = 1。批次完成后的总库存更新：storage' = max(storage − ItemMaxNumber, 0)

满载购物袋 104 的配置是 ItemMaxNumber=80、唯一产出 Weight=100，因此每次都产出面粉，但需要点击 80 次才耗尽批次并启动普通 item CD。Weight=100 是概率权重，不是库存扣减量。

每批次期望钻石 = ItemSpeedUpCost +（StorageSpeedUpCost − ItemSpeedUpCost）÷（StorageMaxNumber ÷ ItemMaxNumber）；每批次期望体力 = ItemMaxNumber × CostEnergy

连续刷新完整库存时，库存耗尽的最后一批用 storage CD 替换 item CD，因此只把两种 CD 的满额价差按批次数分摊。当前加速价仍按剩余比例向上取整；长期期望使用两种 CD 的满额配置价。

如何读下面的母体 series 表

每个可能产出都是单独一列，列标题包含棋子名称、代码和等级；单元格只显示该点击产出的概率。

单次点击产出倍率就是一次点击产出的一级物品等价数量：一级=1、二级=2、三级=4，按概率加权。主:副比例按产出 series 汇总 Weight，主产物取权重最高的 series，其余 series 合并为副产物。

单次点击产出倍率 = Σ[pᵢ × 2^(等级ᵢ−1)]；主:副 = 主产出 series 的总 Weight : 其余产出 series 的总 Weight

概率口径：明细中的百分比是合成结果棋子的 ItemModelConfig.BubbleChance 基础值，不是点击母体时的掉率，也不保证每次合成按该值独立出现。

一次普通合成如何判定

  1. 成功合成产生新棋子后，主棋盘调用 _TrySpreadBubbleByMerge(newItem, targetItem)；棋盘已满或气泡功能未开放时没有通常的概率判定。
  2. 读取新棋子的 BubbleChance（0–100 百分制）；棋盘已有同目标棋子的普通气泡时，本次不再生成。
  3. 命中特殊奖励时可直接设为 100%；否则依次乘订单冗余倍率、同链高等级库存倍率和 BubbleDecreaseModel 倍率，最终以 1% 为下限。
  4. 调用 MathUtil.Random(100)，它使用 Lua math.random() 并转成 1–100 整数；随机值不大于当前概率才在合成位置周围找空位生成气泡。

为何同一棋子出现率会变

  • 订单加成：服务器通用配置 BubbleOrderBonus 允许时，合成当前订单所需棋子的前一级，可直接触发 100%；模式 2 还要求该前一级现有数量不超过 2。
  • 购买连锁：启用 HasBubbleBuyBonus 时，买下的气泡棋子参与下一次合成，可将气泡概率设为 100%。每次合成开始会清除上次记录。
  • 订单衰减：BubbleOrderDecrease 在当前 series 的相关订单需求已由棋盘/库存覆盖时乘一个 0–1 倍率；未配置或条件不满足则不应用。
  • 同链高阶气泡衰减：BubbleChainDecreaseLevel 与 BubbleChainDecreaseRatio 只统计棋盘上高于门槛等级的未打开气泡，按数量乘折减倍率；普通棋子和库存不计入。
  • BubbleDecreaseModel.GetBubbleDecreaseRatio() 还根据未购买气泡等状态给出动态倍率；该模型实现不在目前可读的 Lua 模块中，不能据此宣称固定的保底周期或具体衰减曲线。

哪些因素能确认

玩家等级和母体等级没有作为数字直接进入这段普通气泡抽样公式；但玩家进度决定功能、订单、解锁棋子及远端配置，母体等级改变可产出的子体等级和后续合成机会，因此两者均可能间接改变观察到的频率。母体点击本身不是普通棋子气泡的触发事件。EnergyBubble 等活动能单独产生资源气泡，不能混入普通棋子气泡样本。

客户端采用伪随机数而非可证明的物理真随机。每次符合条件的合成会重新取一个随机值，但概率受状态与远端通用配置影响，并非同分布的固定独立伯努利试验；现有客户端代码也无法证明服务端是否分组、实时下发何种参数。气泡默认 60 秒消失，GetCustomItemBubbleCountdown 可覆盖时长；气泡售价与出现概率是两套配置。

普通路径的抽样阈值 = max(基础 BubbleChance × 订单倍率 × 同链高阶气泡倍率 × 动态倍率, 1)；特殊奖励路径 = 100%；棋盘满 / 功能未开放 / 同目标已有气泡 = 不进入通常抽样

购买连锁强制的精确生命周期

① 破坏气泡

普通购买或免费打开气泡后，主棋盘把该气泡内部棋子类型写入 m_lastBreakBubbleType。
→

② 下一次合成

合成函数入口先把记录清为 nil，再用本次合成来源类型与刚才记录比较；匹配且开关开启时，目标气泡概率直接为 100%。
→

③ 状态结束

这次合成结束后不会保留连锁次数。下一次合成前记录已清空；若中间再破坏新气泡，则新类型覆盖旧类型，只给下一次匹配合成使用。

所以答案是：购买连锁不是“一直触发直到上一个气泡刷新”，而是一次破坏气泡 → 最多影响紧接着的一次匹配合成。如果紧接着的合成来源类型不匹配，该次不会获得 100% 加成，随后记录也会被清掉；如果没有进行合成，记录本身不会因时间自动过期，但下一次合成入口会先清空它。

“远端模式 1 / 2”到底是什么

它不是 Main、Loading 之类的全局游戏模式，也不是玩家等级。代码读取的是服务端通用配置表 GeneralConf 中名为 BubbleOrderBonus 的单独配置项；该项的整数值才是气泡订单加成策略编号：

值在气泡逻辑中的含义额外条件
nil / 0 / 其它订单强制路径关闭回到基础概率及其它倍率计算
1订单所需棋子的前一级合成时，允许直接 100%订单仍有该棋子缺口，且目标配置满足 WeightMultiple=1、有 MergedType
2同样允许直接 100%除上述条件外，前一级棋子在棋盘/库存数量还必须 ≤2

这个值由 GetGeneralConfByType(EGeneralConfType.BubbleOrderBonus, Int) 读取；它是气泡订单加成专用的策略参数。同一套配置框架还包含 BubbleBuyBonus、BubbleOrderDecrease、BubbleChainDecreaseLevel、BubbleChainDecreaseRatio、商店刷新、时间线、库存扩容、屏幕特效等许多互不相同的键。改变其中一个键，不会自动改变其它键。

Gossip Harbor 是否有“全局超参数 / 玩家 tier”系统

  • 确认存在远端配置框架：ConfigModel 从 ServerConfigKey.GeneralConf 加载键值，按 confType 建立 m_generalConfigs；还支持动态配置文件异步加载和文件替换。也就是说，运营可以不更新客户端代码而调整大量功能开关、整数、浮点倍率和时间参数。
  • 确认存在玩家分组相关能力：客户端包含 ABTest、SetABTestGroupInfo、IsPlayerGroupOpen 和活动/排行榜分组数据。说明产品具备实验组、排行榜组或玩家组概念。
  • 不能从当前客户端证明的部分：没有证据表明 BubbleOrderBonus 必然按玩家 tier 分层，也没有看到该气泡参数在客户端按玩家等级二次计算。服务端完全可能向不同账号下发不同 GeneralConf，但具体分组规则、实验比例、持续时间和玩家归组字段不在本地脚本中公开。
  • 最稳妥的判断：“远端模式 1 / 2”是一个由服务端下发的、气泡订单加成专用的策略枚举；它位于一个可广泛调节游戏行为的通用远端配置系统之内，但本身不是统领全游戏的单一难度 tier。

r_order 如何计算：逐步手算规则

这里的 r_order 不是客户端根据概率、玩家等级或订单金币动态拟合出来的数，而是服务端在 GeneralConf 中直接提供的一个浮点参数 BubbleOrderDecrease。客户端只在满足下面的资格检查时使用它；不满足时返回“未应用”，等价于不乘这一层。

r_order = GeneralConf["BubbleOrderDecrease"] 仅当 0 < r_order < 1 且资格检查通过时：p1 = p0 × r_order

资格检查的输入

  1. 读取当前棋盘 + 库存的代码计数：I[c] = GetCodeCountMap(true, false, true)[c]。从调用位置看，这是用于订单/库存比较的合并计数，代码同时纳入棋盘和库存；客户端没有在这里使用“玩家等级”。
  2. 读取 Slot 订单：遍历当前槽位订单的全部需求。只保留需求配置存在且 WeightMultiple == 1 的普通需求项；其它权重类型不会进入本层检查。
  3. 构造订单出现次数：D[c] 是这些订单需求记录中代码 c 出现的次数。反编译代码对每个需求键执行一次 D[c] = D[c] + 1，不是把需求数量字段相加；因此这里更接近“有多少个订单槽位在要这个代码”，而不是完整缺口数量。
  4. 限定到当前合成棋子的 series：根据新棋子类型取得其 chainId，枚举该 chain 的全部等级代码，得到当前 series 的检查集合。
  5. 逐代码比较：对检查集合中存在 I[c] 的代码，取 D[c]（不存在则按 0）；若有任一 I[c] < D[c]，资格失败，返回“不应用”。只有所有比较都通过，才返回配置的 r_order。

手算例子

假设当前合成结果属于面包 series，活跃 Slot 订单中有：订单 A 要 1 个 202，订单 B 也要 1 个 202，订单 C 要 1 个 203。过滤后得到 D[202]=2、D[203]=1。若棋盘+库存计数为 I[202]=2、I[203]=1，且同 series 其它被检查代码也满足比较，则资格通过，若远端下发 r_order=0.6，基础 25% 会变成 25%×0.6=15%。若 I[202]=1，即使当前订单界面仍显示缺口，代码也会因 1<2 返回不应用，概率保持 25%。

重要区别：这层不是“订单还缺多少就按缺口比例衰减”，也不是简单检查当前目标棋子是否已满足；它比较的是当前 series 内、符合 WeightMultiple=1 的订单需求记录数量与棋盘+库存计数。由于 GetCodeCountMap、订单权重配置和服务端参数都可能变化，外部只看订单 UI 未必能准确反推该层是否生效。

N 如何计算：只数棋盘上的高阶未打开气泡

  1. 读取远端整数 L=BubbleChainDecreaseLevel 和浮点数 r_chain=BubbleChainDecreaseRatio。若 L≤0、未配置、r_chain≤0 或 r_chain≥1，本层不应用。
  2. 从本次合成得到的新棋子查出其 chainId，获取该 series 从低到高的完整棋子代码数组 chain[1…M]。如果 M≤L，本层不应用。
  3. 对等级索引 i=L+1…M，把普通棋子代码转为对应气泡代码：数值类型使用 普通代码 + ItemCodeOffset.Bubble，非数值类型使用 ItemCodePrefix.Bubble + 普通代码。
  4. 只读取棋盘计数 B=GetCodeCountMap(true,false,false)。令 N=Σ B[BubbleCode(chain[i])]，没有该气泡代码的项按 0 计。代码只在某个计数为正时才乘 r_chain^计数；全为 0 时返回“不应用”。

N = 棋盘上，同一 series 中等级严格高于 L 的未打开普通棋子气泡总数 r_chain_effective = r_chain ^ N p2 = p1 × r_chain_effective

举例：若门槛 L=5、r_chain=0.5，同一 series 棋盘上有 1 个 6 级气泡、2 个 8 级气泡、3 个 5 级气泡和任意数量已买下的 9 级普通棋子，则 N=1+2=3；5 级气泡没有严格高于门槛，不计；普通 9 级棋子也不计。倍率是 0.5^3=0.125，基础 40% 在不计其它机制时变为 5%。如果这些气泡被购买或过期，下一次合成时 N 重新变小。

同目标气泡去重是独立的前置规则：本次目标棋子的气泡已经在棋盘上时直接不生成，不是再乘一个 r_chain。因此不要把“去重”与“高阶气泡指数衰减”合并计算。

定量计算示例与可观测上限

普通路径某棋子基础 40%，订单倍率 0.50，棋盘高阶气泡倍率 0.25，动态倍率 0.80：
40% × 0.50 × 0.25 × 0.80 = 4%
最终抽样阈值为 4%；不是 40%，也不是“每 2.5 次必出”。
强制路径优先同一合成同时满足订单强制或购买连锁时：
p = 100%
但棋盘满、同目标气泡已存在或找不到空位时，仍可能看不到新增气泡。

对固定状态连续 n 次合成，若暂时忽略状态变化，理论上至少出现一次的概率为 1−(1−p/100)^n；例如固定 40% 时 5 次至少一次为 92.224%，但真实游戏不能直接套用，因为购买、订单缺口、已有气泡和高阶气泡会在每次事件后改变 p。

先给结论：Lucky / Super Lucky 是母体点击之外的独立产出分支。当前客户端能证明它会按母体类型、玩家等级区间和活动模型查表，并且有普通配置与 Generator Boost 配置；但现有反编译材料没有提供 LuckyProduceModel:Try2ProduceLuckyItem 的函数体，因此不能把配置里的 [60,1]、[25,1] 直接宣称为“60% / 25% 的最终触发率”。

一次点击的实际判定链

1 · 进入生成器

GenerateItemCode 先调用 CheckLuckyProduce()；Tutorial 棋盘或不支持 BoostDisco 时直接跳过。
→

2 · Lucky 模型

取得 ActivityType.LuckyProduce 模型，调用 Try2ProduceLuckyItem(m_itemModel)；返回 nil 就走普通产出。
→

3 · 覆盖普通结果

命中时返回 Lucky 产出信息；否则才按母体普通 Weight 池抽取。Lucky 结果不应与普通池概率相加。

P(最终产出 = x) = P(Lucky 触发) × P(x | Lucky 配置) + [1 − P(Lucky 触发)] × P(x | 普通 Weight 池)

配置中的 lucky_items 是 item-weight 列表，例如 204-63 表示候选代码 204、权重 63。若模型采用通常的加权抽样，则候选条件概率为 P(x | Lucky)=w_x / Σw；这部分可以完整手算。super_items 是一组代码白名单，说明这些候选可被 Super Lucky 识别，但当前材料不足以证明它是“第二次独立抽样”、还是对 Lucky 结果的升级标签。

固定还是可调？

  • 可调：母体匹配列表、lucky_chance 数组、Lucky 候选权重、Super 候选集合、level_min/max 都在配置中，不是写死在母体 Weight 表里。
  • 可活动替换：GeneratorBoostLuckyProduceConfig 分为 MoreLuckyProduce 与 ExtraLuckyProduce，同一母体可有另一套候选和参数。
  • 不可由现有文件确定：最终触发率如何由 lucky_chance、能量加成比率、玩家状态合成；Super Lucky 的二次抽样顺序；是否由服务端按账号分组下发。

候选列的百分比是 Lucky 池内部条件概率。右侧“猜测模型”不是客户端已证实语义：暂按 [N,1] = 1/N，并假设“先按 lucky_items 抽取，抽到 super_items 就标记 Super”。

可完整推演的部分与证据边界

本页新增的猜测模型令 q=1/N（例如 [60,1] → 1/60=1.6667%）。若候选总权重为 W，Super 白名单命中的权重为 S，则：P(普通 Lucky)=q，P(Super)=q×S/W，P(x)=q×w_x/W。例如 204-63、205-10、303-15、304-10、305-2 中 Super={205,304,305}，所以 S=22、W=100，猜测 Super 概率为 1/60×22/100=0.3667%。
仍未被证实以上只是用户指定的工作假设。CheckLuckyProduce 只负责调用模型；TryGenerateLuckyItem 还会读取 GetAdjustedMaxEnergyBoostRatio。没有模型函数体或运行时活动下发值时，不能证明“每 N 次一次”、Super 是否只由白名单标记，或是否存在额外升级/保底。

猜测模型：q=1/N；P(Super)=q×Σ[w_i : item_i∈super_items]/Σw；P(x)=q×w_x/Σw。真实模型若不同，表中所有“猜测”列均需重算。

与普通母体 CD 的关系

  • 普通母体点击仍然每次只扣 1 批次库存；Lucky 命中不会把一次点击变成扣多个库存，也不会改变 ItemMaxNumber 的 CD 触发次数。
  • Lucky 产出若是更高等级棋子，会改变“每次点击的实际基础等价”和长期收益；因此母体 CD 表中的普通倍率是不含 Lucky 的基线，Lucky 应作为额外混合分布单独加权。
  • 要从实测反推出 q，必须分开记录普通点击次数、母体 Type、Lucky 特效类型、最终代码和活动状态；只看“出了一个高等级棋子”无法区分普通池、Lucky 还是 Super Lucky。

经济价格拟合：用于估算，不是精确配置公式

把同一 Series 内的等级价格放到对数尺度上回归后，可以得到两个比较稳定、适合人类理解的增长趋势：

商店/普通气泡钻石：D(L) ≈ round(D₀ × 1.90^(L−L₀))
标准订单金币：C(L) ≈ round(C₀ × 1.60^(L−L₀))

解释：在同一条合成链里，棋子每升一级，商店价和普通气泡价通常接近乘以 1.9；标准订单金币通常接近乘以 1.6。D₀/C₀ 是同一 Series 中选定锚点等级的实际配置值，L₀ 是锚点等级。

可靠性：1.90 和 1.60 是跨多条 Series 汇总后的趋势倍率，适合估算数量级、比较增长速度和补全缺失等级的候选值；它们不是客户端明确读取的生成公式。

不能保证逐项命中：价格表由离散整数配置组成，且不同 Series 有不同起点、等级范围、解锁和取整方式。即使允许每个 Series 单独拟合，取整后也不能 100% 复现原表：商店约 67%、气泡约 52%、订单约 18% 的观测点能被独立指数拟合命中。因此精确计算必须优先读取本页棋子明细中的实际价格字段。

直接出售金币是例外：S(L) ≈ max(0, L − k_Series)，当前 193 个棋子中 192 个与此规则一致；个别配置异常仍以明细表为准。

订单金币是否固定

  • 普通主线订单：每个需求棋子的 OrderItemConfig.Price 固定，订单总金币为逐项相加；同一棋子重复出现会重复计价。
  • 游戏历程：玩家等级、进度与订单难度影响棋子是否解锁、能否入选及组合方式，但不会动态缩放该棋子的普通 Price。
  • 基准订单：若配置了 RecommendedPrice，改用该值。当前数据中 1107 为 54 → 42，其余有推荐值的棋子与普通值相同。
  • 最终奖励例外：金币双倍 Buff 将总金币乘 2；Bake Out 等模式可将首项奖励改为活动代币；特殊订单可有独立奖励。
  • 表中“—”表示该棋子没有 OrderItemConfig，不能作为标准随机订单需求，不能凭合成等级外推金币。

三种钻石路径

  • 商店：仅 Slot 存在且 ShopWeight > 0 时算可购买；价格取配置 Price，商品刷新不会按刷新次数自动涨价；ShopCount 是该商品本次投放可买次数，ShopWeight 只参与商品候选抽取。
  • 气泡：表中 BubbleChance > 0 只表示配置上有普通合成气泡的机会，不能保证出现；此版本同时可用的棋子，商店标价与气泡标价一致。
  • 母体 CD：每批长期期望钻石 = item CD 满额价 +（storage CD 满额价 − item CD 满额价）÷ 库存批次数。库存耗尽的最后一批用 storage CD 替换 item CD，因此只摊销两者差额；目标等级 L 只使用不高于 L 的直接产出，并按每升一级需要 2 个低一级棋子递归折算，高等级产出不会倒拆成低等级。体力期望同样按该目标产出数分摊。
  • 未计入：免费等待、部分 CD 折扣、棋盘空间、合成动作、Buff、非目标 series 副产物价值；体力使用配置的每次点击消耗。

订单重复权重衰减的时机

  1. 建立随机订单候选池时，先按当前棋子配置读取 Weight；如果该棋子所属 chain 有运行时重复状态，且配置了正数 RepeatWeightDecrease，候选权重改为 Weight / RepeatWeightDecrease，再与其它有效候选归一化抽取。
  2. 这个状态按 chain 保存，不是单纯按一个 Type 保存；同链棋子可能共享同一重复抑制状态。它只改变候选概率，不改变 Price、DiffScore 或棋子本身。
  3. 候选被选中后，随机订单创建器记录本次选中的 synthesis line/chain，更新持久化的重复状态；因此下一次或后续几次建池可能继续受到衰减。
  4. 完成订单时，客户端遍历本单需求；如果需求配置有 RepeatWeightDecrease > 0，就按该需求的 chain 调用 ResetRepeatWeightDecreaseByChainId。这发生在订单难度累计之后、槽位完成处理之前，是明确的链级重置点。
  5. 另有链级减少逻辑：ReduceRepeatWeightDecreaseByChainId 会把计数减 1，减到 0 后删除状态；反编译代码能确认该接口和持久化，但无法仅凭当前材料把所有调用入口逐一映射到具体 UI 事件。因此“候选选择时更新、相关订单完成时重置、其它配置路径可能逐步减少”是当前最稳妥的生命周期口径。

重复候选有效权重 = 原始 Weight ÷ RepeatWeightDecrease；订单完成重置 = 对本单含该字段的需求逐链清除重复状态

商店刷新与钻石价格

  • 普通商店商品生成时，costCount 直接取该棋子的 ItemPropertyConfig.Price，leftCount 取 ShopCount（缺失时特殊闪购路径使用默认库存）。刷新会重新抽槽位/商品并重新建立这两个值。
  • 因此普通商品的单价是配置固定价，不会因为连续刷新、已购买次数或商品刷新次数自动递增；变化的是商品是否出现、剩余购买次数和候选商品。
  • 手动刷新本身的费用是另一条价格链，代码会根据“本次刷新是否购买过商品/是否连续手动刷新”等状态读取倍率配置；这不是商品 Price，不能与商品单价混为一谈。
  • 闪购/特殊商品可以走独立的 ShopDailyDealsConfig、闪购价格或手动刷新倍率，因此不能把普通商店的固定价结论套到所有活动商店。

关键结论

  • 高级母体的 CD 分摊成本不必然更低。决定因素是 满额加速价增长 与 目标有效产量增长 的相对速度。
  • “钻石/分钟”也不统一。配置同时独立指定时长与满额价；实际价格还因向上取整成为阶梯函数，并在未结束前最低为 1 钻。
  • 低于 1 的母体成本是长期批次的期望分摊，不代表游戏允许支付小数钻石购买单个棋子。
