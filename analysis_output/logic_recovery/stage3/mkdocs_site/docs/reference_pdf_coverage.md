## 仍需区分的证据等级

PDF 是参考分析成果，不等价于当前 APK 的逐函数源码证明。页面已将 PDF 直接给出的数值标为参考快照，将源码能确认的入口、字段和顺序标为源码事实，将缺少真实账号 `FileReplace`、服务器活动 payload、完整亲密度配置或原版运行差分的部分保留为未闭合。这样可以保证“内容不丢失”与“证据不冒充”同时成立。

## 历史配置与证据基线

早期版本曾有独立的“配置索引”和“证据分级”页面；页面重组后内容并入当前站点，规则如下：

### 配置索引

核心本地表仍以当前拆页的完整记录为准：`ItemModelConfig`（548 行）、`Spread`（163 行）、`MergedType`（370 行）、`BubbleChance>0`（138 行）、`OrderItemConfig`（74 行）、`OrderFixedConfig`、`OrderRandomConfig`、`LuckyProduceConfig` 和 `SystemConfig`。这些是包内快照，不代表账号同时启用所有变体；服务端没有本地实际值的字段继续标为 `runtime-pending`。

### 证据分级

- `source-confirmed`：解密/反编译源码或本地配置直接确认。
- `runtime-confirmed`：运行时回放确认对象身份、配置值、时序或结果。
- `runtime-pending`：静态代码已定位，但需要真实运行时、服务端配置或动态对象证据。
- `unavailable`：当前资源没有提供且无法可靠推导，必须说明原因。

底层页面必须把证据状态放在算法和配表旁边；历史推演、模拟输出和远端假设不能提升为 `source-confirmed`。

已完成静态入口、调用顺序、主要状态变化、随机语义和本地配置索引；三类操作已按逻辑树拆分页面。最终运行时验收仍未完成：服务端配置实际值、动态活动对象身份、异步回调时序、网络失败分支，以及原版与复刻版逐字段差分仍需第三阶段回放确认。该状态说明历史分析已归档，不表示 G1–G7 全部放行。
