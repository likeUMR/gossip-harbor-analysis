# Recovery Plan 结构验收记录

本页按 `GH_LOGIC_RECOVERY_PLAN.md` 6.8.8、6.8.8a、6.8.9 和 6.8.10 检查当前 MkDocs。它记录组织质量，不把页面数量当作源码覆盖证明。

## 检查结果

| 检查项 | 结果 | 说明 |
| --- | --- | --- |
| 四个顶层入口 | 通过 | 付费项目、母体点击、棋子拖拽与合成、订单提交均有唯一根页面 |
| 父页与子页职责 | 通过 | 父页讲阶段顺序，子页按对象与动作拆分，末层包含算法/配置 |
| 目录命名 | 通过 | 抽象分组已改为“点击落地与后续事件”“移动、合成与副产物”“交付结算与后续同步”“订单补位与生成” |
| 重复导航节点 | 通过 | 当前导航路径唯一；同名机制仅在真实不同阶段保留 |

| 配置归属 | 通过（静态层） | 页面保留全量本地配表和变体入口；服务端 payload、账号后缀和动态值继续标 `runtime-pending` |

## 结构规则

导航不按源文件排列；每个可见节点都有自己的 `index.md`，末层 `detail.md` 承载具体算法。名称优先使用对象加动作，例如“合成资格”“订单补位与生成”“剪刀拆分”“状态刷新与同步”。具体消费者归入实际触发阶段，不另建孤立的通知或验证栏目。

## 证据边界

本次结构验收不能把源码未解析项、服务端配置或原版回放缺口变成“已完成”。G1-G6 仍按各页面台账状态处理，G7 在缺少原版差分时保持 `unavailable`。这符合 6.8.7、6.8.9 和 6.8.10 的独立门槛。
