# Lucky订单

完成订单只提供一次触发资格，Lucky创建还要检查等级、次数与冷却。需求只从现有且不被其它订单占用的代码中选，重复需求不能超出现有件数；连续次数保存在元数据，不能把它当母体Lucky机会池。

## 内部处理顺序与目的

1. 先消耗本次触发资格，再检查配置、等级、连续次数与冷却。

2. 从未被其它单占用的现有库存建立三个候选池，先决定需求数。

3. 逐项抽代码并扣后续池的可用份数，成功或失败分别更新次数与冷却。

---

## 演示案例

下面分别改变前提，让各条分支实际发生；互斥结果属于不同场景。

### 场景1：库存支持两次同物需求

**本例情境：** 分别演示有资格且库存够用的Lucky建单，以及次数耗尽进入冷却。

**判断与目的：** 消耗触发资格，通过次数门槛后从库存池抽两项，同一代码按实际件数扣后续可用份数。

**玩家看到的结果：** 新Lucky订单需要两件203，现有两件足够；连续次数剩2，缓存中的五件不让需求超量。

### 场景2：最后一点先进入冷却

**本例情境：** 分别演示有资格且库存够用的Lucky建单，以及次数耗尽进入冷却。

**判断与目的：** 最后一点不是再生成一单，而是写入冷却并拒绝本次Lucky创建。

**玩家看到的结果：** 这一次不会出现Lucky顾客；一小时后再次取得触发资格并满足库存条件时，可创建203单需求Lucky订单，新批次3点。
